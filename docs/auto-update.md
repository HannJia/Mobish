# 自动更新与版本发布

> **1.0.10 原生 V3 与更名（2026-11-13）**。软件显示“墨笔生花”，安装器和程序文件名使用 mobish。当前 V3 数据目录固定在原位置，首次安装目录末级为 mobish，升级安装优先沿用已注册目录。旧格式数据、备份与云文档不再读取或升级，旧文件保留原处。完整安装包包含 Electron、字体、OCR 资源与运行库，用户无需安装 Node.js。

## 用户更新

1.0.9 及更早版本按旧文件名识别安装包，无法直接下载 mobish 安装包。请打开发布页手动下载安装当前 1.1.0。1.0.10 起客户端按新文件名检查与下载，可从软件内更新到 1.1.0。

Windows 安装版从 1.0.2 开始支持自动检查和手动检查。1.0.0 / 1.0.1 没有对应代码，需要手动安装一次 1.0.2。只修改 GitHub Release，无法给已经安装的旧程序远程增加更新入口。

1.0.10 的“自动更新”默认开启，启动后约 12 秒检查一次，持续运行时每 6 小时检查。发现新版本并校验更新清单后，在后台下载。设置页可关闭自动下载，关闭后仍每 6 小时检查版本，并显示版本号红点提醒，也可手动检查、下载和安装。

1.0.5 起：检查失败后按 1、5、15、30、60 分钟逐步退避，之后每小时重试；联网恢复、窗口激活、休眠恢复时会检查是否需要补查，失败补查有一分钟节流。这些检查也会在关闭自动下载后继续运行。失败会显示可关闭的状态提示；即使新版更新清单暂时获取失败，也会保留已发现的版本和发布页入口，但不会下载未经验证的安装包。原始 1.0.4 安装包仍采用上面的 6 小时间隔。

下载后由用户点击“安装并重启”。普通关闭软件不会触发安装。AI 任务、联网对话、后台任务、项目导入或保存失败都会阻止安装。浏览器 / 开发环境只展示说明和发布页，不下载或安装桌面更新。

下载完成后，主导航栏左侧的版本号旁显示“更新已准备好”卡片，提供版本、可滚动的更新说明，以及“安装并重启”和“稍后”。卡片避开版本入口，不主动打开模态框或抢占输入焦点；“稍后”收起本次提示，设置页仍能安装。安装按钮仍需明确确认，随后先保存内容，再启动安装程序并重新打开软件。关闭自动下载不会中断已经开始的下载，可使用“取消下载”单独停止；检查期间关闭开关则不会开始自动下载。自动下载关闭时，发现新版后版本号旁显示红点，收起顶部通知后仍保留，点击版本号可查看更新。

## 当前开发调整

1.0.11 将软件更新整合到“设置 → 关于”，保留启动、定时、联网恢复与退避重试的版本检查。关闭“自动更新”后，发现新版会在左下角版本号旁显示红点，由用户手动下载。红点在收起更新通知后继续显示，下载完成后可再次点击版本号查看并安装。

### 下一版：GitHub 优先，Gitee 备用

2026-11-25 登记。GitHub 的 `HannJia/Mobish` 正式 Release 继续作为发版基准，[Gitee 的 hannjia/Mobish](https://gitee.com/hannjia/Mobish) 用于 Windows 客户端的备用更新和国内手动下载。该 Gitee 仓库已导入，当前发行版列表为空。客户端接入和发布链路待下一版实现。

- **检查版本**。自动检查和「检查更新」都先访问 GitHub。网络错误、请求超时、限流、服务错误或返回的发布信息无效时，转查 Gitee 最新正式发行版。两边各自设置有限超时。GitHub 正常返回且已是最新版时，结束本轮检查。若 GitHub 已告知有新版，切换后按同一版本标签取文件，避免使用滞后镜像上的旧文件。
- **下载与安装**。GitHub 的 `latest.yml` 或安装包缺失、下载失败、停滞超时或校验失败时，清理失败的临时文件，改从 Gitee 备用渠道获取同版本的一整套更新文件。继续校验正式版本号、文件名、大小和 SHA-512。用户主动取消下载时结束本轮，安装仍由用户确认。
- **发布与附件**。每次发布从同一次 Windows x64 构建取得安装包和 `latest.yml`，同步正式标签并创建同版本 Gitee Release。Gitee 社区版的发行版单附件上限为 100 MB，GVP 项目为 200 MB，1.1.7 安装包为 165,248,600 字节。发版时核对实际配额。若附件放不下，在 Gitee 发行版提供国内 HTTPS 下载入口，清单和安装包由固定、经验证的国内地址托管。客户端仅访问随程序配置的下载域名，不从发行版正文读取任意安装地址。[Gitee 发行版上传限制](https://help.gitee.com/repository/release/create)
- **下次发布验收**。在 Windows 安装版覆盖 GitHub 正常、GitHub 检查失败或超时、GitHub 下载失败后切换、Gitee 版本滞后、两个渠道都失败、下载校验失败及用户取消。用国内无代理网络实测备用渠道的检查、下载和覆盖升级。1.1.7 仍访问 GitHub，当前无法访问 GitHub 的用户需从国内下载入口覆盖安装一次带有双源逻辑的版本。

## 维护者发布

正式版本发布到公开仓库 `HannJia/mobish`。安装包的 `build.publish` 与客户端更新地址指向该仓库。发布提交应基于公开分支，源码与附件在同一版本下对应。

1. 使用标准版本号，例如 `1.1.0`。同步 `package.json`、`package-lock.json` 顶层及根包版本，更新 `CHANGELOG.md`、首页版本和对应发布说明。
2. 在 Windows 执行测试和构建：

```bash
npm ci
npm run prepare:ocr
npm test
npm run test:update-download
npm run build -- --win nsis --x64 --publish never
npm run test:electron:packaged
node scripts/audit-release.cjs
```

3. 将基于公开历史的正式源码提交显式推送到 `public` 远程的 `main`，为该提交创建并单独推送 `v1.1.0` 标签。推送前审核源文件范围及提交历史。
4. 先创建 GitHub Release 草稿，上传同一次构建产生的文件：

| 文件 | 用途 |
| --- | --- |
| `mobish-1.1.0.exe` | 必需，Windows x64 安装包 |
| `latest.yml` | 必需，包含版本、相对文件名、大小和 SHA-512 |
| `mobish-1.1.0.exe.blockmap` | 构建产生的分块信息，当前版本使用完整下载 |
| `mobish-1.1.0.exe.sha256` | 供用户手动核对的 SHA-256 文件 |

5. 核对 `latest.yml` 中版本、文件名、大小和 SHA-512 与 `.exe` 一致。不要将旧版 `latest.yml` 搭配新版安装包，也不要在构建后单独替换 `.exe`。
6. 填写更新说明，确认全部附件上传完成后再公开 Release，并设为 Latest。不要勾选预发布。

程序读取公开仓库 `HannJia/mobish` 的最新正式 Release，按标准版本比较，只更新到更高版本。发现新版本后，下载清单与安装包固定到该版本标签下，避免检查和下载之间切换到不同版本。

**仅 push 源码或只创建 Git 标签不会触发可下载更新。** 必须发布带正确附件的 Release。缺少清单或安装包时，用户只能打开发布页处理，软件不会尝试安装不完整的版本。

## 安全与测试边界

- 更新检查不需要 GitHub Token，不上传模型密钥或小说资料；公开 API 存在网络与频率限制，出错时可重试或手动下载。
- 下载由 `electron-updater` 执行 SHA-512 校验。当前未配置代码签名，哈希只能验证文件与该发布清单一致，不能替代发布者签名；应保护好 GitHub 账户与发布权限。
- 不关闭系统安全防护，不接受自定义更新仓库、外部安装 URL、预发布、降级或 NSIS Web Installer。
- `test:update-download` 使用隔离本地 HTTP 服务和不可执行的测试内容，验证真实下载器及篡改拦截；不会运行安装程序。
- 自动化状态机测试验证“确认 → 等待保存 → 安装调用”的顺序，以及错误时不调用安装。完整覆盖安装 / 卸载仍应在专用测试设备上验证，不以用户正在使用的数据目录作为测试目标。
